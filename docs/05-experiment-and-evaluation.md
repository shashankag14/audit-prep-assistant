# 5. Proving it works

> **TL;DR**
> - **What to prove:** the brief points auditors to issues they would otherwise find late or miss, **without** showing anything wrong as a Fact or Extracted item.
> - **Smallest experiment:** replay the brief on real past surveillance audits and compare it with what auditors actually found on site. No customer sees anything until that passes.
> - **Already built:** the prototype + an eval runner that checks it against a synthetic gold set with planted issues an auditor should spot during prep.
> - **Convinced when:** in a pilot phase, auditors use the **'Audit Brief'** generated by the system to change what they check on site during the audit, catch more issues with the help of brief, and rarely click **Mark wrong** if they disagree with any of the findings in the brief.

---

## 1. What I want to prove

| # | What to prove | Why | How to check |
| --- | --- | --- | --- |
| 1 | The brief shows the issues that matter (overdue CAs, repeat findings, conflicts, gaps) | Missing an issue is the worst failure (see [01](01-problem-framing.md)) | Compare with findings auditors raised on site |
| 2 | Nothing wrong is shown as **Fact** or **Extracted** | Auditors stop trusting the brief after a few wrong items | Wrong claims on the gold set = 0 |
| 3 | If something can't be checked, the brief says so and why | Gaps must be visible | Every planted gap shows up as **Missing** |
| 4 | Auditors use the brief to decide what to check | A correct brief is useless if nobody acts on it | Pilot: how many brief items get added to the audit plan, and how often auditors click through to the cited source |
| 5 | Prep time goes down | One of the primary pain point | Auditors report their prep time in the pilot |

| Step | What it tells  | Risk |

## 5. How to evaluate before customers see it

### Metrics

| Metric | Target | Why |
| --- | --- | --- |
| Planted issues caught | All | Main goal |
| Wrong claims shown as **Fact** / **Extracted** | **0** | Trust |
| Unexpected **Conflict** | 0 | A false conflict wastes the auditor's time |
| Unneeded **Missing** | Low | Too many "I don't know" and auditors stop using it (assumption #3 in [01](01-problem-framing.md#4-assumptions-id-challenge)) |
| Cross-tenant leaks | **0** | Must never happen |
| Time and cost per brief | TBD |  |

### Eval per step (to see which step failed)

| Step | What to measure | How |
| --- | --- | --- |
| OCR | Text errors | Hard cases set |
| Search | Was the right page sent to the LLM | Gold names the page → **sent** ✓/✗ |
| Extraction (LLM) | Did it return a claim citing the right page | **claim** ✓/✗ |
| Citation check | Made-up quotes always become Missing | Unit tests |
| Verifier | How often **Check source** is right / missed | Gold pairs: quote, claim, does the quote support it? |
| Rules | Exact answers | Unit tests |

## 6. What product outcome would convince me


| Outcome | How to measure | Target (first guess) |
| --- | --- | --- |
| Brief points at real issues | Findings raised on site that the brief flagged / all findings visible before the audit | Better than just using the structured data (via rules) only, eg. ≥ 70% |
| Brief adds something new | Useful items the auditor didn't find in own prep |  |
| Brief is trusted | **Mark wrong** rate on Fact/Extracted items | eg. < 2% and **0 on Fact** |
| Auditors check sources | Share of items where the source was opened | More than 0. If nobody opens sources, they may trust it blindly |
| It changes the plan | Items added to the audit plan | In most audits |
| They keep using it | Still used after 4-6 weeks | Most pilot auditors |
| Time | Prep time reported by auditors | Same or less |

Notes:
- If **'Mark wrong'** stays high after fixes, it means unstrcutured data extraction isn't ready, so we ship the rules-only brief first i.e. only using structured data.
- Nobody opens sources and nobody marks anything wrong -- auditors may rely on it too much. Needs a better UI?
